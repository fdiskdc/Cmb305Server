# 第一章　领取密钥包与登录三台服务器

新任管理员上岗按两步走：**先领钥匙（解压加密凭据包），再开四扇门（SSH、PVE、1Panel、180 网关面板）**。

## 1.1 第一步：领取并解压加密凭据包

三台服务器（180、181、191）管理员所需的 SSH 私钥、登录密码、PVE 二次验证密钥和 1Panel 完整安全入口，已统一打包为 **AES-256 加密压缩包** `login-materials.zip`（位于仓库 `access/login-materials.zip`），包内各文本文件均已写好中文用途注释。

> 【重要：解压密码获取方式】本压缩包的解压密码**不在线上传播，也不写入任何文档或聊天记录**。新任管理员必须**亲自前往实验室机房物理机现场查看**。解压时请使用本地支持 AES-256 的工具（macOS 推荐 Keka 或 The Unarchiver；Windows 推荐 7-Zip 或 WinRAR），**严禁上传至任何在线解压网站**。解压后的材料仅保存在本人受保护的电脑本地目录，切勿上传到公开仓库、聊天群或学生容器中。

解压前，建议先在本地电脑核对压缩包 SHA-256 校验值，确认与仓库 `access/SHA256SUMS` 完全一致：

```bash
# macOS / Linux
shasum -a 256 login-materials.zip

# Windows PowerShell
Get-FileHash -Algorithm SHA256 .\login-materials.zip
```

解压后包内共有 7 个文件，用途如下表（请勿把文件名或二次验证设置密钥当成密码输入）：

| 文件名 | 用途与适用范围 | 使用提醒 |
| --- | --- | --- |
| `ACCESS-README.txt` | 三台服务器完整内网入口总览与注意事项 | 首次解压后先通读一遍 |
| `bnu-305server-1` | 180、181、191 三台宿主机共用的 SSH 私钥 | 仅用于 `ssh -i`，切勿手动编辑或复制正文发群 |

## 1.3 登录方式一：SSH 登录宿主机（180 / 181 / 191）

日常排查、定位账号、管理容器与核验存储，**优先使用 SSH 登录宿主机**。打开自己电脑的终端（macOS 使用“终端”，Windows 使用 PowerShell），进入解压后的凭据目录执行：

```bash
# 1. macOS / Linux 首次使用前必须收紧私钥权限（Windows 可跳过此步）
chmod 600 ./bnu-305server-1

# 2. 登录 180 单臂网关服务器（root 与 cmb305 均支持该私钥）
ssh -i ./bnu-305server-1 -p 8005 root@172.16.95.180

# 3. 登录 181 计算服务器
ssh -i ./bnu-305server-1 -p 8005 root@172.16.95.181

# 4. 登录 191 计算服务器
ssh -i ./bnu-305server-1 -p 8005 root@172.16.95.191
```

Windows PowerShell 只需把路径中的 `./bnu-305server-1` 写成 `.\bnu-305server-1` 即可。首次连接会出现主机指纹确认提示，核对无误后输入 `yes` 回车。

**登录成功后，养成习惯立即跑这两条验明正身命令**，确认没有连错机器：

```bash
hostname && whoami
```

看到什么算正常：180 应返回 `cmb305-management-server`，181 应返回 `cmb305server1`，191 应返回 `Cmb305Server2`，身份应为 `root`（或 180 的 `cmb305`）。若主机名与预期不符，立刻执行 `exit` 退出。

为了以后少敲长命令，可以在自己电脑的 `~/.ssh/config` 中配置三个快捷别名（将私钥路径替换为自己的实际路径）：

```text
Host bnu-180
    HostName 172.16.95.180
    Port 8005
    User root
    IdentityFile ~/.ssh/bnu-305server-1

Host bnu-181
    HostName 172.16.95.181
    Port 8005
    User root
    IdentityFile ~/.ssh/bnu-305server-1

Host bnu-191
    HostName 172.16.95.191
    Port 8005
    User root
    IdentityFile ~/.ssh/bnu-305server-1
```

配置完成后，以后只需在终端输入 `ssh bnu-180`、`ssh bnu-181` 或 `ssh bnu-191` 即可直连。

## 1.4 登录方式二：显示二次验证动态码并登录 PVE 网页端（181 / 191）

181 与 191 两台计算服务器均按**已开启 PVE 二次验证（TOTP）**的标准流程操作。登录时需要先用 `pve2f.txt` 中的 **32 位设置密钥**生成当前有效的 **6 位动态验证码**（切勿把 32 位设置密钥直接粘贴到 PVE 验证码输入框）。

### 第一步：生成并显示 6 位 TOTP 动态验证码（以网页生成器为例）

最直观的方式是使用开源网页工具 **`https://totp.danhersam.com/`**（纯浏览器本地计算，打开即用），按图 1 依次操作：

1. 用浏览器打开 `https://totp.danhersam.com/`。
2. 在 **① `YOUR SECRET KEY`** 输入框中，清空网站自带的示例占位符（`JBSWY3DPEHPK3PXP`），完整粘贴加密包 `pve2f.txt` 中的 **32 位设置密钥**（仅复制密钥正文，去掉注释行与前后空格）。
3. 核对 **② 参数区**：确认 `NUMBER OF DIGITS` 保持 **`6`**、`TOKEN PERIOD (IN SECONDS)` 保持 **`30`**，不要修改。
4. 查看 **③ 动态码显示区**：页面会立即实时生成当前 **6 位数字动态验证码**，上方蓝色进度条会倒计时提示剩余有效秒数（如 `Updating in 21 seconds`）。如果剩余时间不足 5 秒，建议等它自动刷新出下一组数字再填入 PVE。
5. 点击右下角 **④ 复制按钮**，即可一键复制当前 6 位验证码，切回 PVE 弹窗直接粘贴使用。

![图 1　使用 https://totp.danhersam.com/ 显示 6 位 TOTP 动态验证码（图中 JBSWY3DPEHPK3PXP 仅为网站自带示范占位符，实际请粘贴 pve2f.txt 中的密钥）。](00_totp_generator.png)

> 【长期使用与安全提示】如果希望日常更方便地在手机上随时查看，也可以将 `pve2f.txt` 中的同一串 32 位密钥导入手机验证器（如 Google Authenticator、Microsoft Authenticator 或苹果“密码” App，选择“手动输入设置密钥”，参数同样为：基于时间 TOTP / `SHA1` / `6 位` / `30 秒`）。使用网页生成器时，请仅在本人受保护的管理电脑浏览器中使用，用完后关闭标签页，切勿在公用电脑上留存输入历史或截图分享；切勿在 PVE 后台随意增删或修改二次验证配置。

# 第二章　180 单臂转发网关架构与日常运维

## 2.1 180 单臂网关的作用与工作链路

180 服务器（`cmb305-management-server`，`172.16.95.180`，Rocky Linux 10.2）是整个实验室服务器区的**校园网自动认证与单臂转发网关**。它的核心工作逻辑非常直接：

1. **单臂接入**：180 通过单一物理网口 `ens5f0` 连接到实验室交换机 `TL-SG2218P`（`172.16.95.192`）的端口 6；交换机端口 1 上联至校园网默认网关 `172.16.95.1`。
2. **校园网保活**：容器 `campus-auth-180` 定时检测校园网在线状态，掉线后自动使用已启用的校园网认证账号重新登录。
3. **白名单 NAT 转发**：181、191 及实验室其他已登记设备的默认网关均指向 `172.16.95.180`。只有在 180 网关面板中处于 **“已启用 + 已放行”** 状态的 IPv4 设备，才会被 `campus180-forward.service` 放行并做 SNAT 转发上网。

| 核心组件 | 运行形式 | 职责说明 |
| --- | --- | --- |
| `gateway-panel-180` | Docker 容器（HTTPS `18080`） | Web 管理后台（流量总览、设备白名单、校园网认证账号） |
| `gateway-db-180` | Docker 容器（PostgreSQL） | 保存设备授权表与校园网认证账号表 |
| `gateway-sync-180` | Docker 容器 | 将数据库授权快照同步至转发规则库 |
| `campus-auth-180` | Docker 容器（host 网络） | 自动检测校园网在线状态并按需登录 |
| `gateway-switch-meter-180` | Docker 容器 | 每 8 秒采集上联交换机 `TL-SG2218P` 端口 1 实测速率 |
| `campus180-forward.service` | 宿主机 systemd 服务 | 维护 IPv4 放行白名单、转发规则与 SNAT |

# 第五章　共享存储核验、数据边界与备份恢复

## 5.1 共享存储正常基线与核验命令

实验室共享存储统一挂载在宿主机的 `/storage` 下，并自动传播到运行中的用户容器。注意：本地目录名拼作 `storage`，181 的两项 InfiniBand 远端导出名拼作 `strage`（少一个 `o`），核对时须保留原拼写。

| 目录（均在 `/storage` 下） | 正常来源与协议 | 适用节点 |
| --- | --- | --- |
| `/storage/panfs3` | `15.1.1.1:/`（NFSv3，经以太网 `vmbr0`） | 181、191 |
| `/storage/panfs4` | `16.1.1.1:/`（NFSv3，经以太网 `vmbr0`） | 181、191 |
| `/storage/storage_151` | `[fe80::e61d:2d03:22:49b1%ibs13]:/strage_151`（NFSv4.1，经 `ibs13`） | 仅 181 |
| `/storage/storage_152` | `[fe80::e61d:2d03:23:2dd1%ibs13]:/strage_152`（NFSv4.1，经 `ibs13`） | 仅 181 |

**核验顺序：先查宿主机挂载表（不直接 `ls` 远端，防卡死），再查示范容器内挂载，最后再做授权目录试读。**

```bash
# 在 191 宿主机核验（示范容器 CTID 2102）
findmnt --mountpoint /storage/panfs3 -o TARGET,SOURCE,FSTYPE
findmnt --mountpoint /storage/panfs4 -o TARGET,SOURCE,FSTYPE
pct exec 2102 -- findmnt --mountpoint /storage/panfs3 -o TARGET,SOURCE,FSTYPE
pct exec 2102 -- findmnt --mountpoint /storage/panfs4 -o TARGET,SOURCE,FSTYPE
```

```bash
# 在 181 宿主机核验（示范容器 CTID 1102，核查全部四项）
for m in panfs3 panfs4 storage_151 storage_152; do
  echo "=== 宿主机 /storage/$m ==="
  findmnt --mountpoint "/storage/$m" -o TARGET,SOURCE,FSTYPE
  echo "=== CT 1102 /storage/$m ==="
  pct exec 1102 -- findmnt --mountpoint "/storage/$m" -o TARGET,SOURCE,FSTYPE
done
```

> 【共享存储异常三条止损原则】① 如果某个目录未挂载（`findmnt` 无输出），**立即通知用户暂停向该路径写入**，防止文件误写爆宿主机系统盘；② 若怀疑存储端无响应，先记录 `findmnt` 与报错，不要反复执行 `ls` 或强杀进程；③ **181 的 `/etc/fstab` 仍留有旧地址（192.168.3.151/152），切勿执行 `mount -a` 当作恢复手段**。具体网络与挂载修复见第 8.2 节。

## 5.2 四类数据的保护边界与备份现状

做任何维护前必须明确：**普通的 `vzdump` 容器备份只包含容器系统盘，不包含学生的个人绑定目录！** 宿主机上学生个人数据存放在 `/tank/lab-data/users/<用户名>/` 下的三个独立 ZFS 数据集（`home`、`work`、`scratch`）。

| 数据类别 | 所在路径 | 恢复所需材料 |
| --- | --- | --- |
| 容器系统盘 | 容器内 `/etc`、`/usr`、`/opt` 等 | `vzdump` 系统归档（`.tar.zst`）、`container.conf`、软件清单 |

## 6.1 新建容器（标准单槽位新建与批量新建）

## 6.2 彻底删除容器（含彻底清空个人数据 `--purge-home`）

### 先分清三种删除方式，切勿选错命令

**重要提醒**：命令名 `rollback` 并不是“安全撤销”！它直接执行销毁操作。执行前务必根据审批要求核对下表：

| 删除级别 | 使用命令 | 会删除哪些内容 | 适用场景 |
| --- | --- | --- | --- |
| **1. 常规毕业退役（保留 `home`）** | `pve-labctl rollback <槽位>` | 删容器系统盘、DNAT 端口规则、`work` 与 `scratch`；**保留 `home`** | 学生毕业但 `home` 资料仍需保留移交 |
| **2. 彻底删除容器（清空全部数据）** | `pve-labctl rollback <槽位> --purge-home` | 删容器系统盘、DNAT 端口规则，**并彻底销毁 `home`、`work`、`scratch` 及父数据集 `/tank/lab-data/users/<用户名>`（不可逆！）** | 确认已备份并获书面批准，需要彻底清零并回收槽位 |
| **3. 删除非托管手工测试容器** | `pct shutdown <CTID>` 后 `pct destroy <CTID> --purge` | 仅删该测试容器及系统盘（**不清理** `pve-labctl` 端口规则与登记） | 仅限**不在** `pve-labctl list` 中的管理员临时测试容器 |

> 【彻底删除前四方必核清单】执行彻底删除（尤其带 `--purge-home`）前必须全部落实：① 已按第 5.3–5.4 节完成系统盘与个人数据双备份并**通过试恢复校验**；② 用户与课题负责人已确认成果移交完毕；③ 接收人已确认关键文件可打开试跑；④ 管理员已书面批准**彻底清除 `home` 且无需留存**。如只是学生暂时不用，请优先停机或暂停访问，不要直接销毁。

### 彻底删除标准流程（示范参数区 + 简洁分步命令）

**执行位置**：目标 PVE 宿主机（`root`）。

```bash
# ========== 示范参数区（以 191 示范 51 / 2102 演示格式，严禁对示范容器执行！） ==========
SLOT='51'
CTID='2102'
LAB_USER='server29y0odtmde'
BASE_PORT='9000'
# =====================================================================================

# 第 1 步：最后一次交叉核对主机名、槽位、CTID、用户名、挂载与当前 ZFS 数据集
hostname -s
pve-labctl show "$SLOT"
pct status "$CTID"
pct config "$CTID" | grep -E '^(hostname|rootfs|mp[0-9]+):'
zfs list -r tank/lab-data/users | grep "$LAB_USER"

# 第 2 步：先优雅停机，并确认状态已变为 status: stopped
pct shutdown "$CTID" --timeout 120
pct status "$CTID"

# 第 3 步：按审批级别二选一执行（务必看清是否加 --purge-home！）
# 【选项 A】彻底删除容器 + 彻底清空 home / work / scratch 及父数据集（不可逆！）：
pve-labctl rollback "$SLOT" --purge-home

# 【选项 B】常规退役（仅删除容器、端口规则、work 与 scratch，保留 home 目录）：
# pve-labctl rollback "$SLOT"
```

### 第 4 步：彻底删除后必须逐项完成 5 项复核

由于控制器底层清理采用“报错后继续”逻辑（部分销毁失败或 MySQL 推送失败时不会让整条命令非零退出），**绝不能只看命令执行完就收工**，必须运行以下 5 条复核命令确认彻底清干净：

```bash
# 1. 确认 PVE 容器已完全消失（应无输出）
pct list | awk -v id="$CTID" '$1 == id'

# 2. 确认 ZFS 个人数据集与宿主机目录已彻底清空（--purge-home 时均应无输出/不存在）
zfs list -r tank/lab-data/users 2>/dev/null | grep "$LAB_USER" || echo "ZFS 数据集已清空"
ls -ld "/tank/lab-data/users/$LAB_USER" 2>/dev/null || echo "宿主机个人目录已清空"

# 3. 确认旧 DNAT 端口转发规则已全部清除（应无该槽位端口规则残留）
iptables -t nat -S | grep -w "$BASE_PORT" || echo "旧端口规则已清除"

# 4. 确认本地控制器槽位状态已变为 destroyed
pve-labctl list | awk -v u="$LAB_USER" '$2 == u {print $1, $2, $3, $4}'

# 5. 若上一步日志出现 MySQL rollback push failed，手动补推同步或上报技术支持
pve-labctl mysql-sync
```

> 【异常止损】如果复核发现容器、ZFS 数据集、端口规则或数据库状态中有任意一项残留，**切勿重复执行 `pve-labctl rollback` 碰运气，也不要手工随意运行 `zfs destroy`**，先保留完整输出日志交技术支持定点清理。

```bash
scp -P 8005 -i "$KEY" -r "${STAGE}/$(basename "$SRC_RUN")" "root@${DST_HOST}:${DST_INBOX}/"
```

**第 3 步（目标宿主机 191）**：校验完整性并按第 5.4 节恢复个人目录：

```bash
# 在 191 宿主机执行（先核对校验值，全部 OK 后再恢复）
cd /mnt/migrate-inbox/ct-1102-20261123-150000
sha256sum -c SHA256SUMS
```

**第 4 步（验收与切换）**：核对目标用户 UID/GID 映射与软件/Conda 环境，由用户从 191 新入口实测 SSH、网页桌面、读写权限及小样本分析。切换后**只保留一处写入**；旧节点数据保留至约定期限、确认无回退需求后，再单独按第 6.2 节办理旧容器退役或彻底删除。

## 7.3 高级作业：完整系统盘恢复与接管

仅当个人文件迁移无法复现复杂系统级环境时，才由技术维护人执行完整容器系统盘恢复（`pct restore`）。按以下 5 步严格推进：

| 阶段 | 执行要点 | 必须满足的过关条件 |
| --- | --- | --- |
| 1. 准备目标 | 分配空闲已批准 CTID，核验目标空间与归档 `SHA256SUMS` | `pct config` 与 `qm config` 均确认未占用 |
| 2. 恢复个人数据 | 按第 5.4 节恢复 `home`、`work`、`scratch` 并核对 UID/GID | 目标目录校验无误，未覆盖其他用户数据 |
| 3. 隔离恢复系统 | 执行 `pct restore`（参考仓库 `docs/迁移与交接.md` 附录 B.1），附加 `--onboot 0 --start 0 --unique 1` 且先断开网卡 | 恢复后状态为 `stopped`，无 IP 或端口冲突 |
| 4. 对齐配置与接管 | 对照本机模板 `905` 补齐 `/storage` 传播挂载，落实 IP、端口规则与控制器登记接管 | 明确控制器能正确管理该实例；**严禁直接把源节点整份 MySQL 库覆盖到目标机** |
| 5. 小范围验收 | 源端停写，目标启用网络并启动容器，请用户端到端试跑 | 登录、读写、共享存储与小样本均通过后再正式交接 |

## 8.2 专项作业：重启后的共享存储恢复（PanFS 与 InfiniBand）

**适用场景**：宿主机维护或断电重启后，第 5.1 节的共享存储核验未通过。**由熟悉网络与存储的维护人在目标宿主机执行。**

### 第一部分：PanFS 策略路由与挂载恢复（181 与 191）

两台节点连接 `panfs3` / `panfs4` 必须走各自独立的源地址与策略路由表（**两台主机绝不能复用同一源地址**）：

| 参数 | `panfs3`（`15.1.1.1:/`） | `panfs4`（`16.1.1.1:/`） |
| --- | --- | --- |
| 服务端 `H` / 路由表 `TAB` / 优先级 `PREF` | `15.1.1.1` / `53173` / `3173` | `16.1.1.1` / `53174` / `3174` |
| 本机源地址 `SRC` | 181 用 `172.16.95.181`；191 用 `172.16.95.191` | 181 用 `16.1.1.43`；191 用 `16.1.1.191` |
| 正式挂载目录 `DEST` | `/storage/panfs3` | `/storage/panfs4` |

以下以 **191 恢复 `panfs3`** 为示范（恢复 `panfs4` 或在 181 上操作时，按上表替换示范参数区；注意 181 的 `16.1.1.43` 位于地址池内，补配前先确认无冲突）：

```bash
# ========== 示范参数区（以 191 恢复 panfs3 为例，按上表替换） ==========
H='15.1.1.1'
SRC='172.16.95.191'
TAB='53173'
PREF='3173'
DEST='/storage/panfs3'
# ======================================================================

# 第 1 步：只读查看当前接口地址、策略规则与 NFS 路由（已有且正确的项跳过不重复加）
ip -br -4 addr show dev vmbr0
ip -4 rule show
ip -4 route get "$H" ipproto tcp dport 2049

# 第 2 步：（仅 panfs4 缺少源地址时执行）确认无冲突后为 vmbr0 补上源地址
# ip -4 addr add "$SRC/32" dev vmbr0 noprefixroute

# 第 3 步：补齐直连路由与 rpcbind（111 端口）策略规则，并查询服务端真实 RPC 端口
ip -4 route replace "$H/32" dev vmbr0 scope link src "$SRC" table "$TAB"
ip -4 rule add pref "$PREF" iif lo to "$H/32" ipproto tcp dport 111 lookup "$TAB"
ip -4 rule add pref "$PREF" iif lo to "$H/32" ipproto udp dport 111 lookup "$TAB"
rpcinfo -p "$H"
```

根据上面 `rpcinfo -p` 的实际输出，记下 `mountd`（v3/tcp）的真实端口号（此前 `panfs3` 为 `601`、`panfs4` 为 `600`，重启后以实际输出为准），并为输出中的 `nfs`、`mountd`、`nlockmgr`、`status`（如有 `nfs_acl` 一并补齐）的协议和端口逐条添加策略规则：

```bash
# 第 4 步：填入本次 rpcinfo 查到的真实 mountd TCP 端口并补齐策略规则
MD='601'   # 替换为本次 rpcinfo -p 查到的实际 mountd v3/tcp 端口
# 按 rpcinfo 实际列出的协议与端口逐条添加（示例为 2049 与 mountd）
ip -4 rule add pref "$PREF" iif lo to "$H/32" ipproto tcp dport 2049 lookup "$TAB"
ip -4 rule add pref "$PREF" iif lo to "$H/32" ipproto tcp dport "$MD" lookup "$TAB"
# 其余 nlockmgr / status 端口按同样格式逐条补齐后，验证两条关键路由：
ip -4 route get "$H" ipproto tcp dport 2049
ip -4 route get "$H" ipproto tcp dport "$MD"
```

确认两条 `ip -4 route get` 输出均指向 `dev vmbr0` 且 `src` 与上表完全一致后，**先在独立临时目录只读试挂，通过后再正式发布**：

```bash
# 第 5 步：确认 /storage 具备 shared 传播属性，且正式目录未挂载、底层为空
findmnt -n -M /storage -o PROPAGATION
mountpoint -q "$DEST" && echo "已挂载，请勿重复挂载" || echo "当前未挂载，可继续"
ls -A "$DEST"    # 必须为空！若底层已有误写文件，立刻停止并先迁出再挂载

# 第 6 步：在独立临时目录只读试挂验收
TEST_DIR=$(mktemp -d /run/panfs-test-XXXXXXXX)
OPTS="vers=3,proto=tcp,port=2049,mountproto=tcp,mountport=$MD,retry=0"
mount -t nfs -o "ro,nosuid,nodev,nolock,$OPTS" "$H:/" "$TEST_DIR"
findmnt -M "$TEST_DIR" -o TARGET,SOURCE,FSTYPE
ls -AU "$TEST_DIR" | head -n 5
umount "$TEST_DIR" && rmdir "$TEST_DIR"

# 第 7 步：试读无误后，正式读写挂载到 /storage，并按第 5.1 节在宿主机与示范容器双验收
mount -t nfs -o "rw,nosuid,nodev,hard,$OPTS" "$H:/" "$DEST"
findmnt -M "$DEST" -o TARGET,SOURCE,FSTYPE,OPTIONS
```

### 第二部分：181 的两项 InfiniBand 挂载恢复（仅 181）

191 暂无这两条 IB 链路。在 181 宿主机确认 `ibs13` 接口已 UP 且地址可达后，先用只读试挂验收再正式挂载（以 `storage_151` 为示范，`storage_152` 替换为 `[fe80::e61d:2d03:23:2dd1%ibs13]:/strage_152` 与 `/storage/storage_152`）：

```bash
# ========== 示范参数区（仅在 181 宿主机执行） ==========
IB_SOURCE='[fe80::e61d:2d03:22:49b1%ibs13]:/strage_151'
IB_DEST='/storage/storage_151'
# ========================================================

# 1. 先检查 ibs13 状态与正式目录为空
ip -br link show dev ibs13
ls -A "$IB_DEST"

# 2. 独立空目录只读试挂并卸载
TEST_IB=$(mktemp -d /run/ib-test-XXXXXXXX)
mount -t nfs -o ro,vers=4.1,proto=tcp6 "$IB_SOURCE" "$TEST_IB"
ls -AU "$TEST_IB" | head -n 5
umount "$TEST_IB" && rmdir "$TEST_IB"

# 3. 正式挂载并在示范容器 1102 中复核
mount -t nfs -o rw,nosuid,nodev,hard,vers=4.1,proto=tcp6 "$IB_SOURCE" "$IB_DEST"
findmnt -M "$IB_DEST" -o TARGET,SOURCE,FSTYPE
pct exec 1102 -- findmnt -M "$IB_DEST" -o TARGET,SOURCE,FSTYPE
```

## 8.3 停电或整机重启后的恢复顺序

1. **第一步：先恢复并核验 180 单臂网关**。登录 180 网关面板与 SSH，确认 `campus180-forward.service`、容器与校园网认证在线，确保 181/191 均在放行列表中。
2. **第二步：核查 181 / 191 基础设施**。登录宿主机确认主机名、`zpool status -x` 健康、网口正常，对照停机前清单核查应运行的容器（不顺手启动计划停机容器）。
3. **第三步：核查并恢复共享存储**。先用 `findmnt` 确认 191 两项与 181 四项共享盘全部挂载正确；未挂载时先通告暂停写入，按第 8.2 节恢复后再开放。
4. **第四步：示范账号端到端验收**。用 181（`1102`）与 191（`2102`）示范账号从用户网络实测 SSH、网页桌面、共享盘可读性及外网连通性；逐项通告恢复结果并留存记录。
